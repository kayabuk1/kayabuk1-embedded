# AT25SF321B フラッシュログ（Raspberry Pi Pico）

1msごとの記録（1件16バイト）を、走行の制御を止めずにSPIフラッシュメモリへ書き、後からCSVで読み出すためのコードです。

- 割り込み（1msごと）は、16バイトをRAMのバッファに詰めるだけです。SPIは使いません。
- mainのループが、たまった1ページ（256バイト＝16件）をフラッシュに書きます。
- 電源を入れ直した後でも、PCからCSVで読み出せます。

**実機での状況（2026-11-20）**：ブレッドボードの Pico で、約1MHzから約31MHzまでの `i` → `t` → `e` → `l` → `v` が通っています（11/18、モーターを回さない測定。一覧は `測定結果まとめ_20261118.md`）。同じ電源でモーターを回すと、書き込みの命令がICに届かないことがあったので、11/20に「届かなかったページを送り直す」処理を足しました。機体（Pico 2）では、まだ動かしていません。最初に `i` と `t` のコマンドで、通信と書き込みを確かめてください。

## ファイル

| ファイル | 層 | 役割 |
| --- | --- | --- |
| `at25sf.h` / `at25sf.c` | ドライバ | SPIでICと話す（IDの確認、消去、ページ書き込み、読み出し） |
| `flash_log.h` / `flash_log.c` | ログ | 16バイトの記録をためて、1ページずつ書く。CSVで出す |
| `main.c` | アプリ（試験用） | PCからの1文字コマンドで、診断・消去・記録・照合・読み出しを試す |

上の層は下の層の関数を呼ぶだけで、下の層は上の層のことを知りません。機体に載せるときは、`main.c` だけを自分のプログラムに置き換えます。

## 配線

| ICのピン | ブレッドボード（`PICO2350` = 0） | 本番の機体（`PICO2350` = 1） |
| --- | --- | --- |
| 1 CS# | GPIO3 | GPIO13 |
| 2 SO（IC → Pico） | GPIO4（SPI0 RX） | GPIO12（SPI1 RX） |
| 3 WP# | 3.3Vへ（プルアップ抵抗でよい） | 3.3Vへ（プルアップ抵抗でよい） |
| 4 GND | GND | GND |
| 5 SI（Pico → IC） | GPIO7（SPI0 TX） | GPIO11（SPI1 TX） |
| 6 SCK | GPIO6（SPI0 SCK） | GPIO10（SPI1 SCK） |
| 7 HOLD# | 3.3Vへ（プルアップ抵抗でよい） | 3.3Vへ（プルアップ抵抗でよい） |
| 8 VCC | 3.3V（ICのすぐそばで、GNDとの間に0.1µF） | 3.3V（ICのすぐそばで、GNDとの間に0.1µF） |

- ピンとSPIの速さは、`at25sf.h` の先頭で変えられます。
- WP# と HOLD# は、データシート（Table 1）では「ICの中でプルアップされていて、使わないなら浮かせたままでよい」とされています。ただ、11/18の実機（ブレッドボード、SPIは約8.9MHz）では、2本を浮かせたままだと、測るたびに結果が違いました（読み出しに誤りが出た回と、全部合格した回があります）。2本にプルアップ抵抗を入れた測定では、モーターを回さない限り、誤りは出ていません。**つないでおくことを勧めます。**
- VCC（8番）とGND（4番）の間に、ICのすぐそばで0.1µFのコンデンサを入れてください。
- データシートは、CS# を10kΩでVCCにつなぐこと（プルアップ）を勧めています。基板にするときは付けてください。
- SPIの速さは、最初は1MHzにしてあります。11/18のブレッドボードの測定では、約31MHzまで通りました。ただし、モーターの雑音がある機体では、もっと低い速さが限度になります。速さを上げた後は、もう一度 `t` と `e` → `l` → `v` を通してください。

## ビルド

`CMakeLists.txt` の `add_executable` に3つの `.c` を並べ、`hardware_spi` をリンクします（プロジェクト名は、今の `CMakeLists.txt` のものに合わせてください）。

```cmake
add_executable(プロジェクト名
    main.c
    at25sf.c
    flash_log.c
)
target_link_libraries(プロジェクト名
    pico_stdlib
    hardware_spi
)
```

- 今までの `Sample_AT25SF321B_SPI_Flash_Memory.c` は、`add_executable` から外してください（`main` が2つになるため）。`main.c` の中身を、その名前のファイルに入れて使っても構いません（ファイルの名前は、動作に関係しません）。
- ファイルをフォルダに分けるとき（例：`at25sf/`、`flash_log/`）は、`.c` をフォルダ付きで書き、`.h` を探す場所を足します。こうすると、`#include "at25sf.h"` の行は、そのままで通ります。

```cmake
add_executable(プロジェクト名
    main.c
    at25sf/at25sf.c
    flash_log/flash_log.c
)
target_include_directories(プロジェクト名 PRIVATE
    ${CMAKE_CURRENT_LIST_DIR}/at25sf
    ${CMAKE_CURRENT_LIST_DIR}/flash_log
)
```
- `buzzer`、`pico_led_sw`、`pico_rand` は、この3つのファイルでは使っていません。

## まず動かす

シリアルモニタから、1文字ずつ送ります。最初は **`i` → `t` → `e` → `l` → `v` → `d`** の順です。

| コマンド | すること | 正常なら |
| --- | --- | --- |
| `i` | JEDEC ID とステータスを表示 | `JEDEC ID : 1F 87 01`、`SR1 : 00` |
| `t` | 自己診断（最後の4KBで、消す → 読む → 書く → 読み戻す） | `自己診断 : 合格` |
| `e` | ログの範囲（64KB分）を消去 | `ログの範囲の消去の結果 : OK`（実機では、記録の入った状態から約0.18秒、何も書いていない状態から約8ms） |
| `l` | 1msごとに1000件のダミーを記録 | `最後のページまで書けたか : OK`、捨てたページ数 0 |
| `v` | 読み戻して、書いた値と自動で照合 | `照合 : OK` |
| `d` | CSVで出す | 見出し1行と1000行、`records=1000` |
| `s` | 状態（記録した量、かかった時間、ステータスの読み直しの回数）を表示 | 捨てたページ数 0、「06hの後に BUSY=1 と読めた回数」0 |
| `r` | 先頭の64バイトを16進で表示 | |
| `U` | 保護ビットを解除（`ERR_PROTECTED` が出たときだけ） | |
| `C` | チップ全体を消去（データシートでは10〜30秒。実機では、ほとんど何も書いていない状態で約0.8秒） | `チップ全体の消去の結果 : OK` |
| `h` | コマンドの一覧 | |

`e` と `l` は組です。1回の消去につき、記録は1回です。もう一度記録するときは、`e` からやり直します。

表示の例（シミュレータでの出力です。実機では、時間の値が変わります）:

[4] 消去の後に読む（256バイト全部が FF のはず。表示は先頭の16バイト）

```

  （差の 128 バイトは、最後のページの余りを FF で埋めた分です）
捨てたページ数             : 0 ページ（0が正常）
書き込みエラーの回数       : 0 回（0が正常。送り直しても書けなかったページの数）
ページを送り直した回数     : 0 回（0が正常。0でなければ、ICへの命令が届かないことがあります）
--- かかった時間 ---
記録全体の時間                   : 1002 ms（記録を始めてから、最後のページを書き終えるまで）
全ページをICへ送った時間の合計   : 134039 us（63 ページ分）
1ページをICへ送る時間            : 平均 2127 us、最大 2128 us
1ページを送った後、ICが書き終えるのを待った時間 : 最大 389 us
--- 書いた場所と、今の状態 ---
次に書くアドレス 0x003F00 / 記録できる上限のアドレス 0x010F00 / 消去が済んでいる範囲の終わり 0x011000
記録中か = 0、上限まで使い切ったか = 0 （1 なら「はい」）
--- ステータスの読み直し（電源を入れてからの合計）---
06h（書き込み許可）の後に BUSY=1 と読めた回数 : 0 回（0が正常）
消去や書き込みの途中で BUSY=0 と読めた回数   : 0 回
'v' で照合、'd' でCSVを出せます。

```

表示には「件」「ページ」「バイト」の3つの単位が出てきます。1件は16バイト（1msごとの記録1つ）、1ページは256バイト＝16件（フラッシュに1回で書くまとまり）です。

時間は、3つに分けて出します。
- 「記録全体の時間」は、記録を始めてから、最後のページを書き終えるまでの時間です。1000件なら約1秒です。
- 「全ページをICへ送った時間の合計」は、記録全体の時間のうち、mainがSPIの送信にかかりきりになっていた時間です。実機（1MHz）では、63ページで約0.16秒でした。
- 「1ページをICへ送る時間」は、1ページ（256バイト）あたりの時間です。実機では約2.55msでした。「1ページを送った後、ICが書き終えるのを待った時間」は、実機では約0.34msでした。

「ページを送り直した回数」は、0 が正常です。ICが書き込みの命令を受け付けなかったときに、`flash_task()` が同じページを送り直した回数です。送り直して書けた分は、書き込みエラーには数えません。0でなければ、命令がICに届かないことがある、という合図です。

最後の「ステータスの読み直し」は、ステータスの読み取りが、つじつまの合わない動きをした回数です（`t`、`e`、`s` の後にも出ます）。
- 「06h（書き込み許可）の後に BUSY=1 と読めた回数」は、0 が正常です。
- 「消去や書き込みの途中で BUSY=0 と読めた回数」は、実機では、同じ条件でも測るたびに回数が大きく違いました（0回のことも、64KBの消去1回で100回を超えることもあります）。値は、モーターを回さない測定では、どれも `02`（BUSY=0、WEL=1）でした。ドライバは WEL も見て待ち続けるので、結果には影響しません。

CSVをファイルにするには、`=== START DUMP ===` の次の行から `=== END DUMP ===` の前の行までを、PC側で保存します。行数が多いときは、受信した内容をファイルに保存できる端末ソフト（Tera Term のログ機能など）が便利です。

## うまくいかないとき

| 表示 | 確かめること |
| --- | --- |
| `JEDEC ID : FF FF FF` | ICから返事がありません。配線（CS、SCK、SI、SO）、ICの電源、ピンの番号 |
| `JEDEC ID : 00 00 00` | SO の線がGNDに触れていないか、ピンの番号が合っているか |
| IDが 1F 87 01 以外の値 | 値が化けています。SPIの速さを下げる、配線を短くする |
| `ERR_NO_WEL` | 06h（書き込み許可）が届いていないか、ステータスが読めていない。SI、SO、SCK、CS の配線 |
| `ERR_PROTECTED` | 保護ビットが立っている。`U` で解除してからやり直す |
| `ERR_NOT_STARTED` | 消去の命令の後に、BUSYが1になっていない。HOLD# と WP# を3.3Vにつなぐ → SPIの速さを下げる → 配線を短くする、の順に試す |
| `ERR_TIMEOUT` | BUSYが外れない。SO の配線と、ICの電源 |
| `ERR_BUSY` | 1秒待ち直しても、ICが「処理中」と答えている。下に出る `判定に使った SR1` が `FF` なら、ICが答えていない（配線、電源） |
| 「06hの後に BUSY=1 と読めた回数」が 0 でない | 動作は続けられます。一緒に出る SR1 の値を控える。`FF`：ICが答えていない（CS、SO の配線、接触）／`03`：前の処理がまだ続いていた。回数が多いときは、配線を短くする、ICのVCCとGNDのすぐ近くに0.1µFのコンデンサを入れる、HOLD# と WP# を3.3Vにつなぐ、を試す |
| 「ページを送り直した回数」が 0 でない | 記録は続けられます（送り直して書けています）。ICへの命令が届かないことがあるので、配線を短くする、モーターの線から離す、ICのVCCとGNDのすぐ近くに0.1µFのコンデンサを入れる、モーターの端子の間にコンデンサを入れる、を試す |
| 書き込みエラーの回数が 0 でない | 送り直しても書けなかったページがあります（1ページ＝16件が抜けています）。上と同じことを試す |
| 捨てたページ数が 0 でない | mainのループが遅い。ループの中の `printf` や `sleep` を減らす |
| `照合 : NG` | `s` で、捨てたページと書き込みエラーを見る。どちらも0なら、`r` で先頭の値を見る |

11/13に実機で出た「全消去時間がすぐに出る」は、この表の `ERR_NOT_STARTED` にあたる状態です。`t` の [1]〜[3] のどこで止まるかで、原因を切り分けられます。

## 自分のプログラムに組み込む

`at25sf.c`、`flash_log.c` と、2つの `.h` を自分のプロジェクトに入れ、`flash_log.h` をインクルードします。

```c
#include "flash_log.h"

// 1msの制御割り込み（例）
bool control_1ms(repeating_timer_t *t)
{
    // …センサーを読む、モータを動かす…
    now_sensors_data.left_speed  = /* 左の速さ */;
    now_sensors_data.right_speed = /* 右の速さ */;
    log_put(&now_sensors_data);       // 最後に1回。RAMに詰めるだけで、数µsで終わる
    return true;
}

int main(void)
{
    stdio_init_all();
    if (log_init() != AT25SF_OK) {
        // ICと通信できていない。配線を確かめる
    }

    // 走る前（消去は秒単位でかかるので、走り出す前に済ませる）
    log_erase(60 * LOG_BYTES_PER_SEC);   // 60秒分
    log_start();

    while (/* 走行中 */) {
        flash_task();                    // 毎回呼ぶ。すぐに戻る
        // …ほかの処理（長い printf や sleep は入れない）…
    }

    log_stop();                          // 残りを書き終える

    // 後で、PCにつないで
    log_dump();                          // CSVで出す
}
```

`now_sensors_data` は `flash_log.c` の中に用意してあり、`flash_log.h` をインクルードすれば、どのファイルからでも値を入れられます。自分のプログラムに同じ名前の変数があるときは、どちらか一方にしてください。

### 守ること

1. `log_put()` を呼ぶのは1か所だけ（1msの割り込み）にする。
2. `flash_task()`、`log_erase()`、`log_stop()`、`log_dump()` は、mainから呼ぶ（割り込みの中から呼ばない）。
3. mainのループは、`flash_task()` を10ms以内の間隔で呼ぶ。間に合わないと、ページ（16件）単位で記録を捨てます。捨てた数は `log_get_stats()` の `dropped_pages` で分かります。
4. **フラッシュのSPIポートを、割り込みの中で使うデバイス（A/Dコンバータやジャイロなど）と共有しない。** mainがフラッシュに送っている途中に、割り込みが同じポートを使うと、両方の通信が壊れます。本番の設定では、フラッシュは SPI1（GPIO10〜13）を使います。
5. `log_put()` を呼ぶ割り込みと `flash_task()` は、同じコアで動かす。

### 記録できる量と時間

| 項目 | 値 |
| --- | --- |
| 1件 | 16バイト（1ページ256バイトに16件） |
| 1秒（1msごと） | 16,000バイト |
| 全体（4MB） | 262,144件 ＝ 約262秒 |
| 消去の時間 | 64KBにつき標準0.2秒、最大0.7秒。60秒分で、標準なら約3.4秒、最大なら約13秒 |
| 1ページの書き込み | 送信が約2.6ms（1MHz、実機での値）。ICの中の書き込みが標準0.4ms、最大3.4ms（実機では約0.34ms） |

時間の値は、データシート 13.4 の標準値と最大値です。

記録の項目（`Sensors_data_t`）を変えるときは、合計を16バイトのままにして、`flash_log.c` の `log_pack`、`log_unpack`、`log_dump` の3か所も合わせて直してください。

## 確かめたこと

- **ビルド**：Pico SDK 2.3.1 と arm-none-eabi-gcc 13.2 で、Pico（RP2040）と Pico 2（RP2350）向けに、`-Wall -Wextra` の警告なしでビルドできました（シリアルは、USBとUARTの両方の設定で確かめました）。
- **動作（シミュレータ）**：フラッシュICの決まり（書く前に消す、06h が要る、BUSYの間は命令を受け付けない、ページの境界で折り返す、など）をまねたプログラムの上で、この3つの `.c` をそのまま動かしました。
  - `i` → `t` → `e` → `l` → `v` → `d` の一連の流れ
  - 1件〜4000件、4MB全体（262,144件）の記録と、1件ずつの照合
  - 記録の途中の、いろいろなタイミングでの停止
  - 上限まで記録したとき、mainのループが遅いとき、配線が外れたとき、保護ビットが立っているとき
  - 乱数でタイミングをずらした400回の繰り返し
  - 11/16の実機の失敗をまねた場面（消去の途中で BUSY=0 と読める、06h の後に FF が読める、短いCSのHIGHをICが見落とす）。直す前の版は、同じ場面で `ERR_BUSY` などになり、直した版は最後まで進むことを確かめました
  - 11/18のモーターの測定をまねた場面（ICが書き込みの命令を受け付けない）。直す前の版は、ページが書かれていないのに「書き込みエラー 0回」と表示し、直した版は、送り直して全件が読めることを確かめました
- **実機（11/16、最初の版、Pico、SPI 1MHz）**：JEDEC ID `1F 87 01`、自己診断 合格、1000件の記録（捨てたページ 0、書き込みエラー 0）、照合 OK、CSVの出力。1ページの送信は最大約2.5ms、ICの中の書き込みは最大約0.34msでした。
- **実機（11/18、ブレッドボードの Pico）**：SPIの速さ、プルアップ抵抗、コンデンサを変えて25回測りました。一覧は `測定結果まとめ_20261118.md` にあります。
- **まだ確かめていないこと**：11/20の送り直しの、実機での動作。機体（Pico 2、SPI1）での動作。mainのループにほかの処理（LEDやブザーなど）を入れた状態での記録。シミュレータは、割り込みが入るタイミングや、電気的な乱れを、本物ほど細かくは再現できません。

## 11/16の実機テストと、その後に直した所

**起きたこと（事実）**

- 1回目：`i` → `t` → `e` → `l` → `v` → `d` が、すべて通りました。
- 2回目：`t` は合格（データの入った4KBの消去が約27ms、消去後は FF）。続く `e` が、始めてから約20ms後に `ERR_BUSY` で止まりました。
- `e` は「64KBの消去 → 4KBの消去」の順に行います。止まったのは、64KBの消去を「終わった」と判断した後、次の消去の準備（06h の後のステータス確認）で BUSY=1 と読めた所です。

**原因について（ここからは推測です）**

1回の結果からは、原因を1つに決められません。考えられるのは次の3つです。

1. 64KBの消去の途中で、ステータスが BUSY=0 と読めた（読み間違い、またはICの中の状態の行き来）。シミュレータで「消去を始めて約20ms後に、2回続けて BUSY=0 と読める」場面を作ると、直す前の版は、実機と同じ `ERR_BUSY` になりました（同じ症状を再現できた、というだけで、これが原因だと分かったわけではありません）。データの入った4KBの消去に27msかかっているので、64KBの消去が20msで終わったとは考えにくく、今のところ、これがいちばん合います。
2. 06h の後のステータス読み出しに、ICが答えなかった（SO が浮いて FF が読めた）。CSのHIGHが短いと起こりえます。直す前の版は、最適化したビルドの機械語から計算すると、CSのHIGHが数十nsでした（データシートの最小は20ns。計算上は足りていますが、余裕は小さい値です）。
3. 配線の接触や、電源の乱れ。

**直した所**

| 直した所 | 理由 |
| --- | --- |
| 「終わった」の判断を、2回続けて読めたときだけにした。書き込み・消去の後は、WEL が 0 に戻ったことも見る | 1回の読み間違いで、処理の途中に先へ進まないようにする（上の1） |
| 待ち終えた直後に BUSY=1 と読めたら、エラーにせず、待つところからやり直す（1秒まで） | ICが「処理中」と答えているなら、待てば済む（上の1と2） |
| CSをHIGHに戻す前に、SPIが送り終えるのを待つ。HIGHにした後、1µs以上そのままにする | ICがCSのHIGHを見落とさないように、余裕を広げる（上の2） |
| 読み直した回数と、そのときの SR1 を数えて、表示する | 次に実機で動かしたとき、上の1〜3のどれが起きているかを、値から見分ける |

**11/18に分かったこと**

直した版を実機で動かすと、`e` は約179msかかって OK になりました。64KBの消去が約20msで終わることはなく、11/16は「終わった」と判断するのが早かった、と分かりました（事実）。

同じ日に、SPIの速さ、WP#・HOLD# のプルアップ抵抗、ICの電源のコンデンサを変えて、ブレッドボードの Pico（RP2040）で25回測りました。一覧は `測定結果まとめ_20261118.md` にあります。要点は次のとおりです。

- モーターを回さない23回の測定のうち、データの誤りが出たのは、約8.93MHz・プルアップ抵抗なしの1回だけでした。ほかの22回は、約0.99MHzから約31.25MHzまで、`t` と `v` がすべて合格です。
- 消去の途中で BUSY=0、WEL=1（値は `02`）と読めることがあります。回数は、同じ条件でも測るたびに大きく違いました。原因は分かっていません。ドライバは WEL も見て待ち続けるので、モーターを回さない測定では、結果に影響していません。
- 同じ5Vの電源でDCモーターを回すと、読み戻しの誤り、書き込み命令の不成立、照合のNGが出ました。記録中に書き込みの命令がICに届かなくても、そのときの版は気づけませんでした。これを11/20に直しました（次の章）。
- 1ページ（256バイト）をICへ送る時間は、約0.99MHzで約2.5ms、約4.17MHzで約0.61ms、約8.93MHzで約0.29ms、約31.25MHzで約0.09msです。

## 11/20に直した所（届かなかったページの送り直し）

**起きていたこと（11/18、モーターを回した測定）**

- `l`（記録）は「書いたページ数 63、書き込みエラー 0回」と表示したのに、続く `v`（照合）が「0件目が読めません」などのNGになりました。
- NGの多くは、ページの先頭の記録でした。ICが書き込みの命令（02h）を受け付けず、ページがまるごと書かれなかった、と考えると合います（推測）。
- それまでの `flash_task()` は、ページを送った後、BUSY=0 と読めたら「書き終えた」と判断していました。ICが命令を受け付けなかったときも BUSY=0 なので、区別できませんでした。

**直した所**

| 直した所 | 理由 |
| --- | --- |
| `at25sf.c` に `AT25SF_write_state()` を足した。SR1 を1回読み、「書いている」「書き終えた」「書かれていない」の3通りを返す | ICは、書き終えると WEL を0に戻す。命令を受け付けなかったときは、WEL=1 が残る（SR1 = `02`）。true と false の2通りでは、この3つを分けられない |
| `flash_log.c` の `flash_task()` が、ページを送った直後に、ICが受け付けたかを確かめる（`send_page_checked()`） | 受け付けていれば、ICはすぐに BUSY=1 になる。送った直後なら、箱の中身がまだ残っているので、送り直せる |
| 「書かれていない」と2回続けて読めたら、同じページを同じ場所へ送り直す（最大2回） | 1回の読み取りは、読み間違うことがある（11/18の「BUSY=0 と読めた回数」）。送り直しても、同じ場所に同じデータを書くだけなので、データは壊れない |
| 送り直した回数を `log_stats_t` の `write_retries` に数え、`s` で表示する | 送り直して書けた分はエラーにしないが、命令が届かないことがある、と分かるようにする |

**変わらないこと**

- ページを送った後、書き終わるのを待たずに箱を空ける作りは、そのままです。「mainのループは、`flash_task()` を10ms以内の間隔で呼ぶ」という決まりも、変わりません。
- 増える時間は、1ページあたり、ステータスを1回読む分です（約1MHzで20µsほど）。

**この直しでは見つけられないもの**

- ICが命令を受け付けた後に、中で書き込みを取りやめ、WEL も0に戻した場合。
- 送ったデータそのものが、途中で化けた場合。

どちらも、書いた後に読み戻して比べれば見つけられます。時間がかかるので、今は入れていません。

**シミュレータでの確認**

「ICが書き込みの命令を1回だけ無視する」「3回続けて無視する」「最後のページで無視する」「ステータスを1回、または2回続けて読み間違える」の場面を作りました。直す前の版は、ページが書かれていないのに「書き込みエラー 0回」と表示しました（実機と同じ症状）。直した版は、送り直して全件が読めるか、送り直しの上限を超えたときに、エラーとして数えます。

## 11/16の版（1つのファイル）から変えた所
